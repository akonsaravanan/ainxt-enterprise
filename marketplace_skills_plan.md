### Delivery discipline: implement → test → fix → retest, per phase (confirmed by user this round)

Once this plan is fully agreed and implementation actually starts, it is **not** a one-shot "write the code and move on" process. For each phase (1 → 2 → 3 → 4, in order, per the confirmed sequencing elsewhere in this doc):

1. Implement that phase's pieces as designed.
2. Run through **every step in that phase's own verification section** (§1.5, and the equivalent checklists to be written for Phases 2-4 as they're implemented) for real — not just a read-through, actually exercise the UI/API/job.
3. If any step doesn't behave as this plan says it should, **fix it, then re-run the full verification checklist again** — not just the one failing step, since a fix can regress something that passed before.
4. Repeat step 2-3 until every verification step in that phase passes cleanly, *and* the relevant regression checks (each phase's "why this can't break existing systems" table, e.g. §1.4) are re-confirmed — only then move to the next phase.
5. ### 2.2 Reference pattern from Hermes-agent (MIT-licensed, direct source inspection at `C:\Users\localadmin\AppData\Local\hermes\hermes-agent`)

Hermes is MIT-licensed (confirmed via its root `LICENSE` file) — fully compatible with borrowing its *patterns* (not its code) into our MIT project.

- **Slash-command trigger** (`agent/skill_commands.py`): exactly `/skill-name [free-text instruction]`. Names are slugified (lowercase, spaces/underscores → hyphens, strip `[^\w-]`). Supports **stacking**: `/skill-a /skill-b do X` greedily consumes leading `/token`s (capped, e.g. 5) as skill references before treating the rest as the instruction. Skills are resolved against an in-memory index built from project/local/external directories; if a skill's slug collides with a built-in command, it's still reachable via an explicit `/skill <name>` escape hatch instead of auto-registering the collision.
- **Autocomplete** (`apps/desktop/src/store/suggestion-providers/skill.ts`): not a live `/`-dropdown — a "draft mention" scanner that watches the in-progress message text for a whole-word match against any *enabled* skill's name and surfaces a dismissible suggestion pill; clicking it pre-fills `/name ` at the start of the input (doesn't auto-send). Our existing `/`-template dropdown is actually a stronger UX pattern for us to reuse than this — recommend combining both approaches isn't necessary; extend the existing dropdown.
- **"+"-style picker** (`apps/desktop/src/plugins/hermes-bots/skills-hub.tsx`): embeds the skills-hub docs site in an iframe as the primary browse surface, with strict `postMessage` validation (both `event.origin` **and** `event.source` checked) before acting on an "install" message, and the picked identifier is regex-validated before use. We don't need an iframe (our catalog is our own DB, not a hosted docs site) — the relevant takeaway is the **defense-in-depth validation discipline** for anything crossing a trust boundary, and the **provenance-based edit permissions** pattern: `skill-detail.tsx` only allows Edit/Archive when `provenance === 'agent'` (self-authored); hub-sourced/bundled skills are read-only. This maps directly onto our own `created_by`/`third_party` ownership check in Phase 1.

### 2.3 What "configurable" means here (confirmed by user, replaces earlier open question)

The existing UI already has exactly the right primitive — the Skills tab's install toggle is literally labeled **"Use in chat" / "Remove from chat"** (`Marketplace.jsx:588-589`, `675`, `821`), not a generic "Add to Yours" like Connectors/Plugins get. Confirmed semantics for this toggle going forward:

- **Adding** a skill (creating it, uploading it, or it existing as a seed/third-party catalog entry) puts it in the user's skills list/catalog view — visible, but **not yet usable in chat**.
- Clicking **"Use in chat"** is a single **global-for-that-user** switch: once on, that skill becomes invocable via `/skillname` in **every chat that user has**, not just one conversation. This is the toggle Phase 1's `install`/`uninstall` endpoints already implement — no new DB concept needed, just confirming its meaning.
- **Deleting** a skill — whether it's a third-party/marketplace-sourced one or one the user created manually — immediately makes it unusable in **all** of that user's chats, everywhere, not just going forward. Phase 1's `ondelete="CASCADE"` on the install-rows FK plus Phase 2's re-check-at-use-time design (§2.4 below) already deliver this: there's nothing left to look up once the skill row and its installs are gone, so every chat simply stops being able to resolve it, immediately.
- **Explicitly not building right now** (per direct user confirmation): a separate per-user enable/disable layer beyond this single toggle, per-skill configurable parameters/settings, and org/department/role-level availability restrictions. If any of these become needed later, they're additive on top of this model, not a redesign of it.

This resolves the earlier ambiguity cleanly and *simplifies* Phase 2 relative to the first draft below: the per-message attach chip is a **thin, single-send UI convenience** layered on top of the real, global "Use in chat" state, not a second, separate per-conversation backend concept. The `/ask` payload and system-prompt injection still only need a skill's id and its globally-current content; nothing conversation-specific needs to be persisted server-side.

### 2.4 Proposed design (manual-only invocation, global "Use in chat" availability, per-send attachment chip — all confirmed)

**Backend — extend `Question` (`gateway.py`) additively:**
- Add optional `active_skill_ids: List[str] = []` to the `Question` Pydantic model (and equivalents in `KbChat`'s payload, kept in sync per the "must mirror" comment). This list is just *which skill(s) this message invokes* — it is **not** a persistence table; there is no server-side "conversation has these skills attached" row anywhere. The only durable state is the global install (`MarketplaceSkillInstallRecord`, per §2.3); the frontend's chip is local UI memory that simply keeps re-sending the same id(s) on each subsequent message in that chat window.
- In the `/ask` handler, for each id in `active_skill_ids`: verify the current user actually has that skill installed (`MarketplaceSkillInstallRecord` lookup — enforces §2.3's global-use gate server-side, not just client-side) and `security_status != "blocked"` (Phase 4 gate — re-checked at *use* time, not just install time, in case a skill gets blocked or deleted after install/attach). If either check fails, drop that id silently from injection (and let the frontend's next `skillsApi.list()` refresh clear the now-stale chip) rather than erroring the whole chat request. If OK, prepend the skill's `instructions` into the system prompt the same way `agent.system_prompt` is already injected today (`gateway.py:5635-5648`) — reusing that existing composition point rather than inventing a second one.
- This is additive to `Question`/`/ask` — no existing field or branch changes; skipped entirely when `active_skill_ids` is empty (default), so every existing chat flow is unaffected.

### 3.3 Source trust anchoring — guarding against fake/impersonating/illegal marketplaces

This is a distinct concern from Phase 4's content-safety scanning (which catches malicious *instructions* inside an otherwise legitimately-sourced skill). This section is about verifying the *source itself* is who it claims to be, before we ever look at its content:

- **Pin the exact GitHub org identity, not just the name string.** Verified directly via the GitHub API: `anthropics/skills`'s owner is `login: "anthropics"`, `id: 76263028`, `type: "Organization"`. The ingestion job must check the numeric `owner.id` (immutable) against this pinned value, not just match the string `"anthropics"` in a URL — a string match alone would be fooled by a renamed/impersonating account. If the owner id ever doesn't match, halt ingestion and alert rather than silently proceeding.
- **No open-ended discovery.** Deliberately **not** copying Hermes-agent's broad six-source aggregation model (`skills.sh` sitemap crawl, `clawhub`, `lobehub`, `browse-sh`, plus GitHub taps) — that model is built for *maximizing* catalog size across many unvetted sources, which is the opposite of what's being asked for here. Our ingestion job only ever talks to a short, hardcoded allowlist of exact `(org_id, repo_name)` pairs that a human has manually verified once (today: just `anthropics/skills`) — never a search, crawl, or user-submitted URL.
- **Pin commits, not branches.** Already in the plan (§3.2/1.1's `source_ref`) — every ingested skill records the exact commit SHA it came from. This means content can't silently change between our review and a user installing it; a new sync either brings in a new, separately-scanned version, or it doesn't.
- **Anomaly circuit-breaker on the scheduled job.** Since ingestion is now confirmed automatic (not manual per-sync approval), the job needs a Hermes-style health check inverted for our risk: if a single sync run would add/change an abnormally large fraction of skills at once, or the org/owner id check fails, or a previously-Apache-2.0 folder's `LICENSE.txt` disappears or changes to something else — **stop and flag for manual review instead of auto-applying.** Mirrors Hermes's own `EXPECTED_FLOORS` degradation guard (`skills-index-freshness.yml`) but tuned to catch sudden/suspicious change rather than sudden data loss.
- **Every ingested skill is `security_status="unscanned"` until Phase 4's scanner clears it** — sourcing from a verified, legitimate org does not itself imply the content is safe; both checks are mandatory and independent (a legitimate source could still be socially-engineered or compromised upstream; content scanning is the backstop for that).

Ingestion mechanism (mirroring Hermes's twice-daily indexed-and-monitored approach, scaled down, with the above trust anchoring layered in):
- A backend job (scheduled, per the confirmed decision) walks `anthropics/skills`'s tree via the GitHub API (after the owner-id check above), reads each `SKILL.md`'s YAML frontmatter + body plus its folder's `LICENSE.txt`, and upserts a `MarketplaceSkillRecord` with `third_party=True`, `source="anthropics/skills"`, `source_ref="<path>@<commit-sha>"` (pinned), `license` set from the actual fetched license text (not assumed), `created_by=None`, skipping any folder whose license isn't a recognized permissive license (currently: Apache-2.0 only).
- Every ingested skill starts with `security_status="unscanned"` and must pass the Phase 4 gate before it's installable — ingestion populates the catalog, it does not itself grant trust.
- No code execution happens during ingestion — we're only reading markdown + small text files via the GitHub API, never cloning-and-running anything.

This phase is deliberately scoped to research + a design sketch for now — the exact ingestion job's schedule/cadence and the circuit-breaker's exact thresholds are open decisions for the next planning round (see Open Items). **Sequencing note (confirmed by user): Plugins backend work does not start until this entire Skills flow (Phases 1-4) is implemented, tested, and confirmed not to have broken any existing flow.**

```python
class MarketplaceSourceConfigRecord(Base):
    __tablename__ = "marketplace_source_configs_pg"

    id                 = Column(UUID(as_uuid=False), primary_key=True, default=_uuid)
    org_login          = Column(String(255), nullable=False)   # "anthropics"
    org_id             = Column(BigInteger, nullable=False)    # 76263028 — the immutable identity check from §3.3
    repo_name          = Column(String(255), nullable=False)   # "skills"
    enabled            = Column(Boolean, nullable=False, default=False)   # kill switch — off until an admin turns it on
    allowed_licenses   = Column(JSONB, nullable=False, default=list)      # e.g. ["Apache-2.0"]
    sync_interval_minutes = Column(Integer, nullable=False, default=720)  # admin-adjustable cadence, not a hardcoded cron
    anomaly_threshold_pct = Column(Integer, nullable=False, default=20)   # admin-adjustable circuit-breaker (§3.3)
    last_synced_at     = Column(DateTime, nullable=True)
    last_sync_status   = Column(String(20), nullable=True)   # "ok" | "halted_anomaly" | "halted_owner_mismatch" | "error"
    created_by         = Column(String(255), nullable=True)  # which admin added this source
    updated_at         = Column(DateTime, nullable=False, default=_now, onupdate=_now)
```

- The scheduled ingestion job's effective source list is the **intersection** of Layer 1's `MARKETPLACE_SOURCE_FLAGS` env dict and Layer 2's table rows where `enabled=True` — a row with `enabled=True` for a source whose named env flag is `false`/unset is simply skipped (logged, not an error), so an admin can pre-configure/vet a source in the DB ahead of an infra team flipping its named env flag, in either order, safely.

Getting a brand-new source live for real still requires *both* an infra-level env var change *and* an admin-level DB row — never just one.
- A small admin-only API surface follows the same `Depends(get_current_user)` + role-check pattern already used elsewhere (e.g. `PUT /marketplace-skills/{id}`'s ownership/admin check) — exact endpoints are an implementation detail for the next planning round, not designed yet.

## Phase 4: Security & legal validation before a third-party skill becomes usable

### 4.1 What Hermes-agent does (direct source inspection, MIT-licensed, patterns freely reusable)

- **`tools/skills_guard.py`**: a regex-based static scanner (`scan_skill`) classifying findings into categories (exfiltration, prompt injection, destructive actions, persistence, network calls, etc.) and severities, combined with a **trust-tiered install policy** (`INSTALL_POLICY`):
  - `builtin` (their own curated skills) → always allowed.
  - `trusted` (hardcoded allowlist: `openai/skills`, `anthropics/skills`, `huggingface/skills`, `NVIDIA/skills`) → blocks only on a "dangerous" verdict.
  - `community` (everything else third-party) → blocks on "caution" **or** "dangerous."
  - `agent-created` (skills the AI generates for itself at runtime) → prompts a retry on "dangerous" rather than a hard block.
  - A "dangerous" verdict on `trusted`/`community` sources is a **hard block that cannot be force-overridden**.
- **No cryptographic signature verification** of skill content — trust instead comes from: pinned commit SHA (no "always fetch latest," so content can't silently change after review) + (for their *plugins*, not skills) a **sandboxed capability probe**: `hermes_cli/plugin_validate.py` actually imports a plugin and runs its registration in an isolated, disposable child process with a timeout, then diffs *actually-registered* capabilities against what the manifest *declared* — catching under/over-declaration. Skills (pure markdown+text, no code) don't need this — only plugins (which register real tools/hooks) do.
- A **capability-disclosure consent string** (`entry_capability_summary()`) is shown to the user at install time for plugins — i.e., "this will register X, Y, Z" — not silent installation.
- A **kill-list** (`removed.yaml`) blocks reinstalling anything explicitly revoked, even from a stale local cache.

### 4.2 Applying this to our Skills (which are plain instructions + optional supporting text files, not executable code)

Our Marketplace "Skills" are `SKILL.md`-style prompt instructions (plus optional non-executable supporting `files`) — there is currently no code-execution path for a skill in our system (unlike Hermes's CLI-agent, which can run skills as shell/tool actions). This materially lowers the risk surface versus Hermes's plugins, but prompt-injection and social-engineering-via-instructions risk is still real (a "skill" is, after all, text that gets prepended to a system prompt and can try to manipulate model behavior, exfiltrate data via instructed tool calls, etc.), so a scan is still warranted.

**Proposed validation pipeline (design sketch, pending confirmation before implementation):**

1. **Same structural validation as manual creation, always, for every skill regardless of source** — non-empty `name`/`description`/`instructions`, valid `SKILL.md` frontmatter shape (reuses existing `parseSkillMarkdown` validation logic, just also run server-side instead of only client-side, closing a gap where the API could otherwise accept malformed content the UI would have rejected). **Also enforce the real `SKILL.md` spec's length limits, confirmed directly from Anthropic's docs (see the Claude Desktop reference section above): `name` <= 64 characters, `description` <= 200 characters** — this was missing from the original draft of this validation step and must be added to both `parseSkillMarkdown` (client) and this server-side check.
2. **Static content scan** on `instructions` + any `files` content, at ingestion time (Phase 3) *and* re-checked at install time (in case policy/scanner rules changed since ingestion) — a regex/keyword classifier modeled on `skills_guard.py`'s categories (prompt-injection phrasing, instructions to exfiltrate data/credentials, instructions to call destructive or unexpected external actions, obfuscated/encoded payloads). Output populates `security_status` (`passed` / `caution` / `blocked`) on `MarketplaceSkillRecord`.
3. **Trust-tiered policy**, mirroring Hermes exactly in spirit:
   - Our own internally-authored skills (`third_party=False`) → always installable (creator is an authenticated internal user, already accountable via `created_by`).
   - Skills sourced from our **trusted allowlist** (initially just `anthropics/skills`, non-excluded folders) → install blocked only on a "blocked" (dangerous) scan verdict.
   - Any other/community-sourced third-party skill (if ingested later from a secondary source) → install blocked on "caution" **or** "blocked."
   - A "blocked" verdict is a hard stop — no override flag, matching Hermes's "cannot be force-overridden" stance for dangerous findings.
4. **Legal gate** — this already partially exists client-side as `ThirdPartyCheckModal` (shown before installing any `thirdParty: true` item today, per Phase 1's exploration). Two changes: (a) record the user's acceptance server-side (who, when, which skill version) as an audit trail — today it's a client-only confirm with no persistence; (b) surface the skill's `license` field (Phase 3) in that same modal, so the user sees what license they're accepting, not just a generic "this is third-party" warning.
5. **Re-check at chat *use* time, not just install time** (Phase 2's `/ask` handler already does this per §2.4) — if a skill is later flagged/blocked (e.g. a kill-list-style revocation, mirroring Hermes's `removed.yaml`), it stops being injectable into chat immediately, without requiring the user to have re-visited the Marketplace.

**Explicitly not doing (for now, flag if this needs revisiting):**
- No cryptographic signature verification (Hermes doesn't do this for skills either — it relies on pinned SHAs + review, which Phase 3's ingestion design already includes).
- No sandboxed execution probe (not needed — our skills don't execute code; this is a Hermes *plugin*-specific concern, not a skill concern, and we have no code-executing "plugin" backend yet — see Open Items).
